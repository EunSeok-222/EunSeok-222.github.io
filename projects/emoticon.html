손그림 → 이모티콘

스케치북에 대충 그린 낙서를 AI가 twemoji 스타일 동물 이모티콘으로 바꿔주는 딥러닝 프로젝트.

개인 프로젝트 1인 개발 (데이터~학습~배포)
라이브 데모 ↗ GitHub ↗ Deck ↗

01

무엇을 풀려고 했나

손그림 스케치를 twemoji 스타일 동물 이모티콘으로 변환한 결과

이모티콘을 만들려면 보통 그림 실력이나 디자인 툴 사용법이 필요합니다. 저는 "누구나 대충 그린 낙서만으로도 완성도 있는 이모티콘을 가질 수 있으면 어떨까"에서 시작했습니다. 손그림의 서투른 구도는 그대로 살리되, 화풍만 일관된 twemoji 스타일로 바꿔주는 게 목표였습니다.

Stable Diffusion v1.5의 UNet에 LoRA를 파인튜닝하고 ControlNet(scribble)으로 원본 구도를 유지하는 방식을 택했습니다. 데이터셋 정제부터 M1 Mac(MPS)에서의 학습, Streamlit 앱 배포까지 전부 혼자 진행했습니다.

02

구현 포인트

Epoch별 평균 Loss 곡선

  • 손그림 전처리 — 정방형 패딩 + 이진화(흑백)로 ControlNet에 최적화된 입력 생성
  • LoRA 파인튜닝 — PEFT 네이티브 포맷으로 여러 epoch 학습, 최종적으로 epoch 7 채택
  • Apple Silicon 대응 — torch.backends.mps 자동 감지, PYTORCH_ENABLE_MPS_FALLBACK=1로 M1 환경 학습
  • 학습 리포트 — Streamlit 멀티페이지로 학습 곡선·EDA·가중치 분석·생성 품질 비교 제공

03

기술 스택

영역사용 기술
생성 모델Stable Diffusion v1.5(runwayml/stable-diffusion-v1-5) · ControlNet(lllyasviel/sd-controlnet-scribble)

04

막힌 지점과 해결

01loss는 계속 낮아지는데, 생성된 이미지는 한 얼굴이 깨져서 반복됨
증상

학습 epoch를 늘릴수록 loss 그래프는 꾸준히 내려갔는데, 실제로 생성해보면 후반 epoch일수록 오히려 한 얼굴 패턴이 깨진 채 반복 생성되는 과적합 붕괴가 나타났습니다.

원인

당연히 loss가 가장 낮은 마지막 epoch(E6 근처)가 제일 좋을 거라고 생각했는데, 수치 지표와 시각 품질이 따로 놀고 있었습니다. loss는 학습 데이터에 대한 재구성 오차일 뿐이라, 데이터가 적은 상태에서 계속 학습하면 모델이 특정 패턴을 과도하게 외워버려도(과적합) loss 자체는 계속 낮게 나올 수 있었습니다.

해결

수치 최저점이 아니라 시각 품질이 가장 좋은 epoch(E7)를 직접 눈으로 비교해 채택했습니다. 근본적으로는 데이터를 5배 증강하고 dropout 0.1을 추가해 과적합 자체를 줄였습니다.

배운 점

생성 모델에서는 loss가 낮다고 결과물이 좋다는 보장이 없습니다. 지표가 좋은데 실사용이 나쁘면, 지표가 측정하는 대상 자체를 의심해야 한다는 걸 체감했습니다.

02학습률을 조금만 올려도 사람·동물 얼굴이 뒤섞임
증상

학습률(lr) 1e-4로 학습했더니 결과물에서 원본 손그림 구도가 무너지고, 사람 얼굴과 동물 얼굴 특징이 뒤섞인 이상한 이미지가 나왔습니다.

원인

LoRA는 원본 모델 가중치에 작은 변화만 더하는 방식인데, lr이 높으면 그 변화량이 과도해져 ControlNet이 잡아주는 구도 정보를 압도해버립니다. 결과적으로 원본 형체가 거의 남지 않게 된 것이었습니다.

해결

lr을 10배 낮춰 1e-5→5e-6로 조정했습니다.

배운 점

LoRA처럼 "가볍게 얹는" 파인튜닝 방식일수록, 학습률이 조금만 높아도 원본 조건(ControlNet 구도)을 쉽게 뭉개버릴 수 있다는 걸 배웠습니다.

03M1에서 fp16으로 학습하면 loss가 nan
증상

학습 속도를 높이려 fp16(half precision)으로 돌렸더니 몇 스텝 지나지 않아 loss가 nan으로 발산했습니다.

원인

M1 Mac의 MPS 백엔드는 fp16 연산에서 수치 안정성이 떨어져, 특정 연산에서 오버플로우가 나며 loss가 무너졌습니다.

해결

정밀도를 fp32로 강제 전환하고, GPU 메모리 여유가 없는 M1 환경 특성상 batch_size=1로 병행 조정했습니다. 추가로 PyTorch MPS 백엔드가 아직 구현하지 않은 일부 연산자에서 런타임 에러가 났는데, PYTORCH_ENABLE_MPS_FALLBACK=1 환경변수로 미지원 연산만 CPU로 자동 폴백하도록 처리했습니다.

배운 점

fp16은 항상 "더 빠르고 가벼운 선택"이 아닙니다. 하드웨어·백엔드별로 수치 안정성이 다르므로, 속도보다 학습이 끝까지 도는 게 먼저라면 fp32부터 시작하는 게 안전했습니다.

04로컬에선 잘 되던 앱이 배포하자마자 OOM·에러 연발
증상

로컬에서는 문제없이 돌아가던 앱이 무료 배포 환경에 올리자마자 메모리 부족(OOM), 스케줄러 IndexError, 이미지 업로드 403 에러가 연달아 터졌습니다.

원인

세 문제 모두 원인이 달랐습니다 — 무료 배포 환경의 메모리 한도 초과, 사용한 스케줄러 설정이 배포 환경 버전과 불일치, 그리고 XSRF 보호 설정이 업로드 요청을 차단하고 있었습니다.

해결

Hugging Face Spaces 16GB 사양으로 이전하고, 스케줄러를 DPMSolver로 교체하고, XSRF 보호를 비활성화했습니다.

배운 점

"로컬에서 됐다"는 배포 환경에서도 된다는 뜻이 아닙니다. 특히 무료 티어 배포는 메모리·라이브러리 버전 제약이 로컬과 다르다는 걸 배포 직전이 아니라 개발 중반부터 염두에 둬야 했습니다.

05

배운 점과 한계

가장 크게 남은 것 — 생성 모델은 정량 지표(loss)와 실제 품질이 어긋날 수 있다는 걸 직접 겪었습니다. 결국 사람이 눈으로 비교하는 과정을 학습 파이프라인 안에 넣어야 했습니다.

남은 한계 — twemoji 스타일 동물 이모티콘이라는 좁은 도메인에 맞춰 파인튜닝했기 때문에, 다른 화풍이나 사람 캐릭터로 확장하려면 재학습이 필요합니다. 또 무료 배포 환경(HF Spaces)에 의존하고 있어, 트래픽이 몰리면 응답 속도가 느려질 수 있습니다.

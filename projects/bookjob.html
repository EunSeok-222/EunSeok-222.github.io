01

무엇을 풀려고 했나

라이브 서비스(www.bookjob.co.kr) 메인 화면 — 브랜드 컬러인 핑크(#EC4899) 기반

출판업계는 일반 채용 플랫폼에서 소외되어 있어, 업계 특화 구인·구직 채널과 소통 공간이 부족했습니다. bookjob은 채용 공고·구직 게시판과 자유게시판을 하나로 묶어, 출판인이 일자리도 찾고 서로 소통도 할 수 있는 공간을 만드는 걸 목표로 했습니다.

2인 팀이 도메인을 나눠 맡았고, 저는 메인·마이페이지·관리자·PWA·인증을 담당했습니다. 실제 도메인(bookjob.co.kr)으로 2025년 3월부터 지금까지 운영 중인 장기 프로젝트라, 기능 추가만큼이나 코드가 오래 유지보수 가능한 구조를 만드는 게 중요했습니다.

04

막힌 지점과 해결

01관리자 메뉴가 늘어날 때마다 페이지네이션·필터링을 매번 새로 짬
증상

관리자 페이지 컴포넌트 내부에 useEffect와 API 호출 로직이 뒤섞여 있어 코드가 계속 길어졌고, 페이지 전환 시 목록이 잠깐 비었다가 다시 채워지는 깜빡임이 눈에 띄었습니다.

원인

데이터 패칭·페이지네이션·필터링 로직이 UI 컴포넌트 안에 그대로 박혀 있어, 새 관리자 메뉴를 추가할 때마다 같은 로직을 복붙해야 했습니다. 또 페이지를 넘길 때 이전 데이터를 유지하지 않고 바로 로딩 상태로 비워버리는 기본 동작이 깜빡임의 원인이었습니다.

해결

UI 컴포넌트는 뷰만 담당하게 하고, 데이터·비즈니스 로직은 TanStack Query 기반 Custom Hook으로 캡슐화했습니다. keepPreviousData 옵션으로 페이지 전환 시 이전 데이터를 유지한 채 새 데이터로 교체해 깜빡임을 없앴습니다.

배운 점

View와 데이터 로직을 분리하니 컴포넌트 코드가 약 30% 줄었고, 다른 관리자 메뉴를 추가할 때 같은 훅 패턴을 재사용할 수 있었습니다. 관심사 분리는 코드량뿐 아니라 다음 기능을 추가하는 속도에 더 크게 영향을 줬습니다.

02코드 변경이 UI에 어떤 영향을 주는지 배포 전엔 알 수 없었음
증상

2인 팀이지만 각자 다른 컴포넌트를 만지다 보니, 한쪽의 스타일 변경이 다른 화면의 버튼·카드 디자인을 미묘하게 깨뜨리는 일이 배포 후에야 발견되곤 했습니다.

원인

공용 컴포넌트(Button·SearchBar 등)를 상태별(placeholder·size·width)로 눈으로 검증할 방법이 없었고, 코드 리뷰만으로는 실제 렌더링 결과까지 확인하기 어려웠습니다.

해결

Storybook으로 공용 컴포넌트를 상태별 카탈로그로 만들고, Chromatic을 연동해 빌드마다 이전 스냅샷과 자동으로 비교(시각 회귀 테스트)하도록 했습니다. 변경된 UI가 있으면 PR에서 바로 Accepted/Deny로 검토할 수 있게 됐습니다.

배운 점

Storybook·Chromatic 도입 이후 사이트 이탈률이 38% → 28%로 개선됐습니다. 디자인 일관성 문제가 실제 사용자 이탈로 이어지고 있었다는 뜻이었고, 디자인 시스템은 협업 언어이자 지표 개선 수단이라는 걸 체감했습니다.

05

배운 점과 한계

가장 크게 남은 것 — 깜빡임 제거, 뷰 전환 기억, PWA 설치 흐름처럼 작은 디테일이 사용 경험을 좌우한다는 걸 배웠습니다. '돌아가게'를 넘어 '편하게'를 설계하는 감각이 생겼습니다.

다시 한다면 — Custom Hook 패턴을 관리자 페이지에만 적용했는데, 프로젝트 초반부터 전체 도메인에 동일한 패턴을 세웠다면 리팩토링 없이 처음부터 일관된 구조로 갔을 것 같습니다.

남은 한계 — 장기 운영 프로젝트라 브랜치 전략·커밋 컨벤션·리뷰 게이트를 갖췄지만, 2인 팀이라 리뷰가 한 명에게 몰리는 구조적 한계는 여전히 남아있습니다.

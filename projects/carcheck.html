CarCheck

차량 손상 사진 한 장으로 AI가 "보험 처리할지 자비로 고칠지"까지 계산해주는 상담 앱.

개인 프로젝트 1인 개발 (기획~배포 전체)
라이브 데모 ↗ GitHub ↗ Deck ↗

01

무엇을 풀려고 했나

YOLOv8n-seg 학습에 사용한 차량 손상 데이터셋 샘플

사고가 나면 대부분 "이거 보험 처리하는 게 나을까, 그냥 자비로 고칠까"부터 고민합니다. 그런데 이 판단에는 손상 정도·예상 수리비·보험 할증액까지 다 따져봐야 해서, 막상 사고 현장에서는 감으로 결정하는 경우가 많습니다.

CarCheck은 사진 한 장으로 손상 탐지 → 수리비 추정 → 보험 할증 대비 손익 계산 → LLM 상담까지 이어지는 파이프라인을 만들어, 이 판단을 데이터 기반으로 바꾸는 걸 목표로 했습니다. 데이터 수집·전처리부터 YOLOv8 파인튜닝, RAG·LLM 상담 로직, Streamlit 앱까지 전 과정을 혼자 설계·구현했습니다.

02

핵심 기능

🔍 손상 탐지
긁힘·파손·분리·찌그러짐 4종 손상을 10개 부위 기준으로 픽셀 세그멘테이션
💰 수리비 추정
손상 유형별 실제 공임 데이터(SQLite)와 매칭해 항목별 예상 수리비 산출
📊 보험 손익 계산
할증 기준(1~3년, 10~15%)을 반영해 보험처리 vs 자비처리 중 유리한 쪽 추천
💬 LLM 상담
Groq 다중 모델 fallback + Gemini 비상 fallback으로 안정적 응답, RAG 검색 근거 첨부

04

막힌 지점과 해결

01무료 LLM API가 예고 없이 죽고, 완전히 끊겨도 서비스는 살아있어야 함
증상

같은 코드인데 LLM 상담 응답이 간헐적으로 실패했습니다. 특정 시점부터 계속 실패하는 패턴이었습니다.

원인

Groq의 무료 모델이 예고 없이 decommissioned(서비스 종료) 처리되면서, 하드코딩해둔 모델명 호출이 그대로 죽고 있었습니다. 무료 API에 기대는 개인 프로젝트 특성상, 모델 하나에 의존하면 언제든 서비스가 끊길 수 있다는 걸 뒤늦게 깨달았습니다.

해결

모델명을 하드코딩하지 않고 llama-3.3-70b-versatile → llama-3.1-8b-instant → llama3-8b-8192 → mixtral-8x7b-32768 순으로 순차 재시도하도록 바꾸고, 에러 메시지에 decommissioned/model_not_found가 포함될 때만 다음 모델로 넘어가게 분기했습니다. 이 4개 모델이 전부 실패하면 Gemini로 비상 전환하고, 그마저도 실패하면 손상 분석·수리비·보험 손익 데이터를 규칙 기반 마크다운 템플릿으로 즉시 조합해 응답하도록(_fallback_report) 만들었습니다.

배운 점

외부 API에 기대는 기능은 "느려짐"이 아니라 "완전히 죽음"까지 가정해야 합니다. 최후의 fallback을 LLM 없는 규칙 기반 응답으로 만들어두니, 무료 API 3개가 동시에 막혀도 서비스 자체는 멈추지 않았습니다.

02특정 손상 유형만 유독 잘 못 잡음
증상

Scratched(긁힘)는 잘 잡히는데, 찌그러짐·파손 같은 다른 손상 유형은 실제 사진에서 자주 놓쳤습니다.

원인

학습 데이터를 클래스별로 세어보니 Scratched가 전체의 65%를 차지하고 있었습니다. 모델 구조나 학습 방식의 문제가 아니라, 데이터 자체가 한쪽으로 쏠려있던 것이 원인이었습니다.

해결

AI Hub의 공개 데이터로 소수 클래스만 골라 15~18배 확장한 뒤 재학습했습니다.

배운 점

탐지 성능이 떨어질 때 모델부터 의심하기 쉬운데, 먼저 클래스별 데이터 분포를 세어보는 게 더 빠른 진단이었습니다.

03Streamlit에서 업로드한 사진이 갑자기 사라짐
증상

사진을 업로드하고 다른 조작을 하면 방금 올린 이미지가 화면에서 사라지거나 깨졌습니다.

원인

Streamlit은 사용자가 뭔가 조작할 때마다 스크립트 전체를 다시 실행(rerun)하는데, session_state에 PIL 이미지 객체를 그대로 저장해두고 있었습니다. rerun 사이에 그 객체 참조가 깨지는 경우가 있었습니다.

해결

PIL 객체 대신 원본 bytes로 저장하도록 바꿔, 재실행되더라도 항상 바이트에서 새로 이미지를 복원하게 했습니다.

배운 점

Streamlit처럼 매 상호작용마다 스크립트가 다시 도는 프레임워크에서는, 세션에 저장하는 값이 재실행에도 안전하게 재구성 가능한 형태(원시 바이트 등)인지를 항상 의심해야 합니다.

04챗봇이 차량 상담과 무관한 질문에도 답변
증상

테스트 중 "점심 메뉴 추천해줘" 같은 서비스와 무관한 질문에도 챗봇이 성실하게 답변하고 있었습니다.

원인

system prompt에 주제 제한이 없어서, LLM이 일반 어시스턴트처럼 모든 질문에 답하려 했습니다.

해결

system prompt에 차량 손상·보험 상담 주제로 한정하는 규칙을 추가했습니다.

배운 점

LLM은 기본적으로 "뭐든 도와주려는" 방향으로 동작하기 때문에, 서비스 범위를 벗어난 질문을 걸러내는 건 별도로 명시하지 않으면 저절로 되지 않습니다.

05

배운 점과 한계

가장 크게 남은 것 — 혼자 기획부터 배포까지 진행하면서, 모델 성능만큼이나 "외부 의존성이 끊겼을 때 뭘 보여줄 것인가"를 설계하는 게 서비스 완성도에 크게 영향을 준다는 걸 배웠습니다.

남은 한계 — 수리비 추정은 공개된 공임 데이터 기반이라 실제 정비소·지역별 편차를 반영하지 못합니다. 보험 손익 계산도 일반적인 할증 규정을 기준으로 한 추정치라, 개인별 보험 조건(가입 등급, 특약 등)까지는 반영하지 않습니다.

01

무엇을 풀려고 했나

회의 종료 커맨드 실행부터 노션 기록까지 실제 동작 모습

"북잡(Bookjob)" 팀은 디스코드 음성 채널로 자주 회의를 했는데, 회의가 끝나면 누군가 녹음을 다시 들으며 안부 인사·잡담은 걸러내고 회의 내용만 골라 회의록으로 정리해야 했습니다. 1~2시간짜리 회의를 매번 그렇게 사람이 직접 듣고 추려내는 시간이 반복적인 부담이었습니다.

NoteFlow AI는 음성 수집 → 압축 → Gemini 요약(사담 필터링) → 노션 기록까지 이어지는 파이프라인을 만들어, 회의가 끝나는 순간 핵심 액션 플랜만 남은 회의록이 노션에 자동으로 쌓이게 하는 걸 목표로 했습니다. 디스코드 봇 설계부터 음성 처리, Gemini·Notion API 연동까지 전 과정을 혼자 구현했습니다.

핵심 기능

🎙️ 음성 수집·병합
디스코드 음성 채널의 유저별 PCM 스트림을 저장 후 자동 병합
📦 고효율 오디오 압축

100만 토큰 이상 컨텍스트 윈도우로 1~2시간 회의도 한 번에 요약
🧹 사담 필터링
프롬프트 엔지니어링으로 안부·농담 제외, 미참석자는 요약 표에서 자동 제외

요약 내용을 마크다운 파싱(볼드·헤딩·리스트·표) 후 블록 단위로 업로드

디스코드 참여자를 노션 Attendees에 연결, 참석 인원으로 전체/프론트/백엔드 회의 자동 판별

04

막힌 지점과 해결

01디스코드 원본 PCM을 일반 플레이어·API가 읽지 못함
증상

디스코드에서 받은 음성 스트림을 그대로 저장하면, 어떤 플레이어로도 재생이 안 되고 Gemini에 업로드해도 오디오로 인식되지 않았습니다.

원인

디스코드가 주는 순수 PCM 데이터에는 파일 헤더가 없습니다. 샘플레이트·채널 수 같은 메타데이터가 없으니 일반 디코더는 이 데이터를 오디오로 해석할 방법이 없었습니다.

해결

fs로 유저별 PCM 바이너리를 직접 이어붙여 병합한 뒤, FFmpeg에 -f s16le -ar 48000 입력 옵션을 강제로 지정해 "이 데이터는 48kHz 16비트 PCM"이라고 명시적으로 알려주고 MP3로 변환했습니다.

배운 점

헤더 없는 raw 데이터를 다룰 때는 포맷을 추측시키지 말고, 인코더에 원본 스펙을 명시적으로 알려주는 게 가장 확실한 해결책이었습니다.

02긴 회의 파일을 업로드하면 서버가 죽음
증상

1시간이 넘는 회의를 요약 요청하면 서버가 응답 없이 멈추거나 프로세스가 종료됐습니다.

원인

오디오 파일을 Base64로 인코딩해 Gemini 요청 본문에 그대로 실어 보내고 있었는데, 긴 회의일수록 이 문자열이 커지면서 서버 메모리를 다 써버리는 OOM(메모리 부족)이 발생했습니다.

해결

GoogleAIFileManager로 오디오 파일을 클라우드 스토리지에 먼저 업로드하고, 본문에는 그 파일의 URI만 담아 Gemini에 전달하도록 바꿨습니다.

배운 점

대용량 바이너리는 요청 본문에 직접 실어 보내지 말고, 별도 업로드 후 참조(URI)만 전달하는 경로가 서버 안정성에 훨씬 유리합니다.

03AI 요약본을 노션에 그대로 넣으면 서식이 다 깨짐
증상

Gemini가 만든 마크다운 요약을 노션 페이지에 그대로 붙이면 헤딩·볼드·리스트·표가 전부 텍스트로만 남았고, 긴 문단은 업로드 자체가 실패했습니다.

원인

노션 API는 마크다운 문자열을 그대로 받아주지 않고 블록 단위 JSON 구조를 요구하며, 블록 하나당 2,000자 제한도 있었습니다.

해결

요약본을 줄 단위로 파싱해 ###(헤딩)·**(볼드)·-/*(불릿)·|(표) 등을 각각 대응하는 노션 블록 타입으로 변환하는 커스텀 마크다운 파서를 직접 구현했습니다.

배운 점

외부 협업 툴에 콘텐츠를 자동 기록하려면, 그 툴의 데이터 모델(여기선 블록 구조·글자 수 제한)을 먼저 파악하고 변환 계층을 별도로 두는 게 안전합니다.

04잘 되던 노션 저장이 SDK 업데이트 이후 전부 실패
증상

기존에 문제없이 동작하던 회의록 저장 기능이 어느 순간부터 전부 에러를 내며 실패했습니다.

원인

Notion SDK v5에서 databases.query 함수가 제거되고 data_source 개념이 새로 도입되면서, 기존 database_id 기반 페이지 생성 코드가 더 이상 동작하지 않는 상태였습니다.

해결

고수준 헬퍼 함수 대신 notion.request로 저수준 API를 직접 호출하도록 전환해, SDK 버전 변화의 영향을 받지 않는 방식으로 우회했습니다.

배운 점

외부 SDK의 메이저 버전업은 예고 없이 기존 함수를 제거하기도 합니다. 저수준 API 호출로 전환할 수 있는 여지를 미리 알아두면 이런 breaking change에도 빠르게 대응할 수 있었습니다.

05

배운 점과 한계

가장 크게 남은 것 — 회의 종료 커맨드 하나로 녹음부터 노션 기록까지 완전히 자동화되면서, 팀에서 회의록 정리에 쓰던 시간과 인력 부담을 실제로 없앨 수 있었습니다. 외부 API(디스코드·Gemini·노션) 각각의 제약을 먼저 파악하는 게 전체 설계 시간을 크게 아껴준다는 것도 다시 확인했습니다.

남은 한계 — 사담 필터링은 프롬프트 엔지니어링에 의존하고 있어, 회의 주제가 자유로운 잡담형 회의에서는 필터링 정확도가 낮아질 수 있습니다. 노션 사용자 매핑도 NOTION_USER_MAPPING 환경변수로 수동 등록해야 해서, 팀원이 바뀔 때마다 설정을 갱신해야 하는 점은 개선 여지로 남아 있습니다.
